# X1: Restore the C1 order of RATING_SCALE (BBB- before BB+) in src/ratings/notch.mjs and pin it with a literal regression test

## User story
As a credit analyst (through the POC screens that import `src/ratings/notch.mjs`), I want the rating scale back in the C1 order, so that every notch count and WL across the BBB-/BB+ boundary (investment grade to sub-investment grade) is right again.

## Traces to
Plan AC-1, AC-2 and AC-3. AC-4 and AC-7 are covered only through the T-01 contract file, which must pass unchanged. REQ-06-02, C1, C2, X-scale-shape. Finding F-1: commit `84e2366` "refactor: tidy the rating scale" swapped `BBB-` and `BB+`.

## Acceptance criteria
1. (AC-1) Given `import { RATING_SCALE } from "./src/ratings/notch.mjs"`, when it is read, then:
   - `assert.deepStrictEqual(RATING_SCALE, ["AAA","AA+","AA","AA-","A+","A","A-","BBB+","BBB","BBB-","BB+","BB","BB-","B+","B","B-","CCC+","CCC","CCC-"])` passes;
   - `RATING_SCALE.length === 19`;
   - `Object.isFrozen(RATING_SCALE) === true`.
2. (AC-1) Given `RATING_SCALE`, when `RATING_SCALE.push("D")` or `RATING_SCALE[0] = "X"` runs, then a TypeError is thrown and the scale still deep-equals the list in criterion 1 (the scale is still built with `Object.freeze([...])`).
3. (AC-1, AC-2) Given `RATING_SCALE`, when an index is looked up, then `indexOf("BBB") === 8`, `indexOf("BBB-") === 9`, `indexOf("BB+") === 10`, `indexOf("BB") === 11`.
4. (AC-2) Given valid ratings, when `notchChange(previous, current)` is called, then `("BBB+","BB+")` → `3`, `("BB+","BBB+")` → `-3`, `("BBB","BBB-")` → `1`, `("BBB-","BB+")` → `1`, `("BB+","BB")` → `1`, `("AAA","CCC-")` → `18`.
5. (AC-3) Given a downgrade across the boundary, when `notchCalculator` is called, then `("BBB+","BBB-")` deep-equals `{ notches: 2, direction: "downgrade", wl: 1 }`, `("BBB+","BB+")` deep-equals `{ notches: 3, direction: "downgrade", wl: 2 }`, `("BBB","BBB-")` deep-equals `{ notches: 1, direction: "downgrade", wl: 0 }`.
6. (AC-1) Given `test/ratings/notch.test.mjs`, then it has a test that compares `RATING_SCALE` with `assert.deepStrictEqual` (or `deepEqual` from `node:assert/strict`) against the 19 ratings written out literally in the test file in the C1 order; the list is not derived from the module, sorted or built in a loop. Its expected values stay at C1 (`notchChange("BBB+","BB+") = 3`, `("BBB+","BBB-") = 2`, `("AAA","CCC-") = 18`).
7. (AC-1 to AC-4, AC-7, AC-8) Given the fix is committed on the card branch, then:
   - `node --test test/ratings/notch.test.mjs test/integration/ratings/notch.contract.test.mjs` reports `# fail 0` (today 153 tests, 26 failing);
   - `git diff --name-only 84e2366..HEAD` lists only `src/ratings/notch.mjs` (plus `test/ratings/notch.test.mjs` if touched);
   - `git diff 84e2366..HEAD -- test/integration/ratings/notch.contract.test.mjs` is empty;
   - `git diff 4c9b2f7 HEAD -- src/ratings/notch.mjs` is empty: the source is exactly T-01's merged version.

## Edge cases
- Only the swap is reverted: `notchChange`, `notchCalculator`, validation, error messages and exports stay byte-identical.
- Neighbours `BBB` (8), `BBB-` (9), `BB+` (10), `BB` (11) are each exactly 1 notch from the next. A swap anywhere else is caught by the literal deep-equal.
- Scale ends: `AAA` at 0, `CCC-` at 18.
- Normalised input crosses the boundary too: `notchChange("bbb-"," BB+ ")` → `1`; `notchCalculator(" Bbb+ ","bbb-")` → `{ notches: 2, direction: "downgrade", wl: 1 }`.
- Dropping `Object.freeze` fails criteria 1 and 2.
