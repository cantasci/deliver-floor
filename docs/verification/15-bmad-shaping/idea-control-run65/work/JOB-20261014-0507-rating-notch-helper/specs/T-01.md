# T-01: notch.mjs: RATING_SCALE, notchChange, notchCalculator

## User story
As a credit analyst (and as any POC module that works for one), I want one helper that counts the notches between two S&P-style ratings and turns that count into a Watchlist level (WL), so that I no longer count notches and look up WLs by hand.

## Acceptance criteria
1. (AC-1) Given `src/ratings/notch.mjs`, when a test does `import { RATING_SCALE } from "../../src/ratings/notch.mjs"`, then `RATING_SCALE` deep-strict-equals `["AAA","AA+","AA","AA-","A+","A","A-","BBB+","BBB","BBB-","BB+","BB","BB-","B+","B","B-","CCC+","CCC","CCC-"]`, `RATING_SCALE.length === 19`, `RATING_SCALE[0] === "AAA"` and `RATING_SCALE[18] === "CCC-"`.
2. (AC-1, PM detail) Given the imported `RATING_SCALE`, when `Object.isFrozen(RATING_SCALE)` is evaluated, then it is `true`, and `RATING_SCALE.push("CC")` throws `TypeError` (ESM is strict mode). After that, `notchChange("CCC-","CC")` still throws `RangeError`.
3. (AC-1) Given the module, when it is imported, then `typeof notchChange === "function"` and `typeof notchCalculator === "function"`.
4. (AC-2) Given `current` is worse than `previous`, when `notchChange(previous, current)` is called, then it returns the positive integer `indexOf(current) - indexOf(previous)`: `("AAA","AA+")` → `1`, `("BBB-","BB+")` → `1`, `("BBB+","BBB-")` → `2`, `("BB+","BB-")` → `2`, `("BBB+","BB+")` → `3`, `("B","CCC-")` → `4`, `("AAA","CCC-")` → `18`. Each result passes `Number.isInteger`.
5. (AC-3) Given `current` is better than `previous`, when `notchChange` is called, then it returns the negative step count: `("BB+","BBB+")` → `-3`, `("BBB-","BBB")` → `-1`, `("CCC-","AAA")` → `-18`.
6. (AC-3) Given equal ratings, when `notchChange` is called, then the result satisfies `Object.is(result, 0)` (exactly `+0`, never `-0`) for `("BBB","BBB")`, `("AAA","AAA")` and `("CCC-","CCC-")`.
7. (AC-3) Given every ordered pair `(a,b)` of the 19 ratings, when both directions are computed, then `notchChange(a,b) === -notchChange(b,a)`.
8. (AC-4) Given an argument that is not exactly one of the 19 `RATING_SCALE` strings, passed as `previous` or as `current`, when `notchChange` is called, then it throws an instance of `RangeError`. It never throws `TypeError` and never returns. This holds for every value in the "Invalid ratings" test table.
9. (AC-4) Given the same invalid values as `previous` or `current`, when `notchCalculator(previous, current)` is called, and also with an explicit valid `indicator` (`11`, `12`, `13`), then it throws `RangeError`. Examples: `notchCalculator("BBB+","Baa1")` and `notchCalculator("__proto__","AAA",11)`.
10. (AC-4) Given a missing argument, when `notchChange("BBB")`, `notchChange()`, `notchCalculator("BBB")` or `notchCalculator()` is called, then it throws `RangeError`.
11. (AC-6) Given two valid ratings and no third argument, when `notchCalculator(previous, current)` is called, then it returns a plain object whose `Object.keys(...).sort()` deep-equals `["direction","notches","wl"]`, with `notches === notchChange(previous, current)`, `direction` `"downgrade"` when `notches > 0`, `"upgrade"` when `< 0` and `"unchanged"` when `=== 0`, and `wl` from the Ind. 12 mapping (≤0 → 0, 1 → 1, ≥2 → 2).
12. (AC-6) Given those inputs, when `notchCalculator` is called, then `("BBB+","BB+")` deep-strict-equals `{ notches: 3, direction: "downgrade", wl: 2 }`, `("AAA","AA+")` gives `{ notches: 1, direction: "downgrade", wl: 1 }`, `("BB+","BBB+")` gives `{ notches: -3, direction: "upgrade", wl: 0 }` and `("BBB","BBB")` gives `{ notches: 0, direction: "unchanged", wl: 0 }`.
13. (AC-7) Given `indicator` is `11` or `13`, when `notchCalculator(previous, current, indicator)` is called, then `wl` is `0` for a change ≤ 1 (any upgrade, no change, or 1 notch down), `1` for exactly 2 notches down and `2` for 3 or more down. `notches` and `direction` are as in criterion 11.
14. (AC-7) Given those inputs, when `notchCalculator` is called, then `("AAA","AA+",13)` gives `{ notches: 1, direction: "downgrade", wl: 0 }`, `("BBB+","BBB-",13)` gives `{ notches: 2, direction: "downgrade", wl: 1 }`, `("BBB+","BB+",11)` gives `{ notches: 3, direction: "downgrade", wl: 2 }`, `("AAA","CCC-",11)` gives `{ notches: 18, direction: "downgrade", wl: 2 }` and `("BB+","BBB+",13)` gives `{ notches: -3, direction: "upgrade", wl: 0 }`.
15. (AC-7) Given any valid pair, when `notchCalculator(p,c,12)` and `notchCalculator(p,c,undefined)` are compared with `notchCalculator(p,c)`, then all three deep-strict-equal each other.
16. (AC-7) Given a valid pair, including the no-change pair `("AAA","AAA")`, when `indicator` is any of `10`, `14`, `0`, `"12"`, `null`, `NaN`, `12.5`, then `notchCalculator` throws `RangeError`. The indicator is validated even when the WL would be 0.
17. (AC-9) Given any valid pair, when `notchChange` or `notchCalculator` is called, then the result is not a `Promise` (`!(r instanceof Promise)` and `typeof r?.then !== "function"`), and two calls with the same arguments give deep-strict-equal results.
18. (AC-9) Given every call made in criteria 4–16, when the calls are done, then `RATING_SCALE` still deep-strict-equals the list in criterion 1.
19. (AC-9, NFR-security) Given the source text of `src/ratings/notch.mjs`, when it is inspected, then it has no `import` statement, no dynamic `import(`, no `require(`, no `eval(` and no `new Function`. `package.json` has no `dependencies` key.
20. (AC-10) Given the source, when a reviewer reads it, then `notchChange` and `notchCalculator` each have a JSDoc block with `@param` for every parameter (`indicator` documented as optional, `11 | 12 | 13`, default `12`), `@returns`, and `@throws {RangeError}`. `RATING_SCALE` has a JSDoc block stating its type (frozen array of 19 strings), its best-first order and that it holds the only accepted symbols.

## Edge cases
- Boundaries of the scale: the first and last entries (`"AAA"`, `"CCC-"`) are valid as both `previous` and `current`. The maximum is `|18|`.
- The IG/HY crossing `("BBB-","BB+")` is an ordinary 1-notch step. It gets no special treatment.
- WL thresholds, Ind. 12: notches `-1` → 0, `0` → 0, `1` → 1, `2` → 2, `18` → 2.
- WL thresholds, Ind. 11/13: `-1` → 0, `0` → 0, `1` → 0, `2` → 1, `3` → 2, `18` → 2.
- `-0` must never come out of `notchChange`, and `notches` in the calculator must never be `-0` either: `Object.is(notchCalculator("AAA","AAA").notches, 0)`.
- Prototype-property names (`"__proto__"`, `"constructor"`, `"toString"`, `"hasOwnProperty"`, `"valueOf"`) must throw `RangeError`. A lookup through a plain-object map is the trap here; use array membership or a `Map`.
- The error path itself must not throw `TypeError`. Building the message from a `Symbol("BBB+")` or `Object.create(null)` argument through string interpolation throws `TypeError`, so these must still end in `RangeError` (covered by AC-4's "any argument … never throws TypeError").
- A `String` object (`new String("BBB+")`) is not exactly one of the 19 strings and throws `RangeError`.
- Several invalid things at once, such as an invalid rating and an invalid indicator: any `RangeError` is fine. Which one is reported is not part of the contract, and the message text is not part of the contract either.
- Extra arguments beyond the third are not specified and are not tested.
