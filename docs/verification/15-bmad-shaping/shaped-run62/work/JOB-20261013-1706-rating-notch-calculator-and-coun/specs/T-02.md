# T-02: Indicator 12: countryRatingChangeWl (REQ-03-12) on top of notchChange, with unit tests

## User story
As a credit analyst (through the POC form that imports this indicator), I want the Indicator 12 Watchlist level for a client's country rating change, so that a downgrade of the country rating is scored by the Ind. 12 rule and an invalid rating is never scored.

## Acceptance criteria
Module: `src/indicators/countryRating.mjs`. Its only named export is `countryRatingChangeWl(previous, current)`, which returns the number 0, 1 or 2. It is built on `notchChange` from `../ratings/notch.mjs` (T-01, not modified here).

1. AC-11 [P0] (Ind. 12 is a Must; a wrong threshold under-scores a client's country risk with no workaround): Given a previous and a current country rating, when `countryRatingChangeWl(previous, current)` is called, then it returns, strictly equal:
   - `("BBB","BBB-")` → `1`
   - `("BBB","BB+")` → `2`
   - `("BBB","BB")` → `2`
   - `("AAA","CCC-")` → `2`
   - `("BBB","BBB")` → `0`
   - `("BBB-","BBB")` → `0`
   - `("BB","BBB")` → `0`
2. AC-11 [P0]: Given all 361 ordered pairs `(p, c)` of `RATING_SCALE`, when `countryRatingChangeWl(p, c)` is called, then the result is:
   - `0` when `notchChange(p,c) ≤ 0`;
   - `1` when it is `=== 1`;
   - `2` when it is `≥ 2`;
   - always `typeof === "number"` and one of `0`, `1`, `2` (strict equality).

## Edge cases
- Boundaries of the Ind. 12 rule: notches -1 → 0, 0 → 0, 1 → 1, 2 → 2, 3 → 2, 18 → 2, -18 → 0. The function never returns 3 or 4, a string, a boolean, `null` or `undefined`.
- The two rules also differ at 2 notches: the calculator gives WL 1, Ind. 12 gives WL 2. Both values are already pinned by AC-8 and AC-11, and this is consistent with the two rules. The required comment covers the 1-notch case (B-36). Mentioning the 2-notch case as well is allowed but not required.
- Trim and validation come only from `notchChange`. So `countryRatingChangeWl(" BBB ","BBB-") === 1`, and `countryRatingChangeWl("bbb","BBB-")` throws `RangeError` with exactly the same message `notchChange` gives.
- Both invalid: only `previous` is named, inherited from `notchChange`. Valid previous with invalid current: the current value is named.
- `Symbol("x")` and `{}` reach the caller as `RangeError`, never as `TypeError`.
- No override or third parameter. Extra arguments do not change the result: `countryRatingChangeWl("BBB","BBB-", 0) === 1`.
- A QA test must never spawn `npm test`. AC-16 is checked by running the command, not from inside a test file.
- Node 22's `node --test` runs every `.mjs` file under a `test/` directory. Any helper module that QA puts under `test/` must therefore have no side effects. Better: keep helpers inside the test file.

## Test design
Unit tests are written by the dev in `test/indicators/countryRating.test.mjs`. They import `countryRatingChangeWl` from `../../src/indicators/countryRating.mjs`, and `RATING_SCALE`, `notchChange` and `notchCalculator` from `../../src/ratings/notch.mjs`. Give the file one top-level `describe` named after the module (e.g. `"indicators/countryRating"`) so QA can spot it in the `npm test` output.

QA integration tests go in `test/indicators/qa/` (files `qa-*.test.mjs`, e.g. `qa-indicators-consumer.test.mjs` and `qa-indicators-purity.test.mjs`). Every QA test name starts with `qa-indicators:` so it is unique in the repo. QA imports both public modules the way a downstream consumer does, and reads source files with `node:fs`, stripping comments before grepping.
