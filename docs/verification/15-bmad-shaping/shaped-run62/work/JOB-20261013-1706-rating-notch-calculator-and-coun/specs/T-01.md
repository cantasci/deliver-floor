# T-01: Ratings core: RATING_SCALE, notchChange and notchCalculator (REQ-06-02) with unit tests

## User story
As a credit analyst (through the POC modules that import this library), I want the signed notch change between a previous and a current rating and the Watchlist level that change produces, so that a downgrade gets the right distance and the right WL, and an invalid rating is never scored.

## Acceptance criteria
Module: `src/ratings/notch.mjs`. It has named exports only: `RATING_SCALE`, `notchChange`, `notchCalculator`. Scale indexes 0..18: AAA, AA+, AA, AA-, A+, A, A-, BBB+, BBB, BBB-, BB+, BB, BB-, B+, B, B-, CCC+, CCC, CCC-.

1. AC-1 [P0] (a wrong or reordered scale gives every caller a wrong distance and WL): Given `import { RATING_SCALE } from "../../src/ratings/notch.mjs"`, when it is read, then `assert.deepStrictEqual(RATING_SCALE, ["AAA","AA+","AA","AA-","A+","A","A-","BBB+","BBB","BBB-","BB+","BB","BB-","B+","B","B-","CCC+","CCC","CCC-"])` passes, `RATING_SCALE.length === 19` and `Array.isArray(RATING_SCALE) === true`.
2. AC-2 [P2]: Given `RATING_SCALE` in strict ESM code, when a caller tries to mutate it, then `Object.isFrozen(RATING_SCALE) === true`, and each of `RATING_SCALE.push("CC")`, `RATING_SCALE[0] = "X"` and `RATING_SCALE.length = 0` throws `TypeError`. Afterwards the array still deep-equals the AC-1 list.
3. AC-3 [P0] (a wrong sign or distance flips a downgrade into an upgrade and under-scores the client): Given two valid ratings, when `notchChange(previous, current)` is called, then it returns the integer `RATING_SCALE.indexOf(current) - RATING_SCALE.indexOf(previous)`.
   - Each of the 18 adjacent pairs `RATING_SCALE[i] → RATING_SCALE[i+1]` returns `1`, and each reverse pair returns `-1`.
   - Pinned: `notchChange("BBB+","BB+") === 3`, `("BBB+","BBB-") === 2`, `("AA","A+") === 2`, `("BB","BBB") === -3`, `("A-","A") === -1`, `("AAA","CCC-") === 18`, `("CCC-","AAA") === -18`.
4. AC-4 [P2]: Given the same rating twice, when `notchChange(r, r)` is called for each of the 19 steps (e.g. `notchChange("BBB","BBB")`), then the result is `0` and `Object.is(result, 0) === true` (never -0).
5. AC-5 [P0] (an unscorable rating that yields a number produces a wrong WL): Given an invalid rating in either position, the other being `"BBB"`, when `notchChange` is called, then it throws an instance of `RangeError` and returns nothing. This applies to each of the 15 pinned values, in both positions (30 calls):
   - strings: `"CC"`, `"C"`, `"D"`, `"SD"`, `"NR"`, `"Baa1"`, `"XYZ"`, `"bbb+"`, `""`, `"   "`;
   - non-strings: `null`, `undefined`, `42`, `{}`, `Symbol("x")`.
   - Example: `assert.throws(() => notchChange("NR","BBB"), RangeError)` and `assert.throws(() => notchChange("BBB", null), RangeError)`.
6. AC-6 [P2]: Given an invalid rating, when `notchChange` throws, then the `RangeError` message contains the value as it was passed:
   - `" cc "` → contains `" cc "` (untrimmed); `"Baa1"` → `"Baa1"`; `null` → `"null"`; `undefined` → `"undefined"`; `42` → `"42"`; `{}` → `"[object Object]"`; `Symbol("x")` → `"Symbol(x)"`, and the error is a `RangeError`, not a `TypeError`.
   - `previous` is checked first: the message of `notchChange("XX1","XX2")` contains `"XX1"` and not `"XX2"`.
   - Tests check the type and the contained text only, never the full wording.
7. AC-7 [P2]: Given a valid rating with surrounding spaces, when `notchChange(" BBB+ ", "BB+")` is called, then it returns `3`. `notchChange("BBB", " BBB ")` returns 0 with `Object.is(result, 0) === true`.
8. AC-8 [P1] (the analyst sees a wrong notch count or WL; the workaround is counting by hand): Given a previous and a current rating, when `notchCalculator(previous, current)` is called, then the result `deepStrictEqual`s, with exactly 3 keys:
   - `("BBB+","BB+")` → `{ notches: 3, direction: "downgrade", wl: 2 }`
   - `("BBB+","BBB-")` → `{ notches: 2, direction: "downgrade", wl: 1 }`
   - `("AA","A+")` → `{ notches: 2, direction: "downgrade", wl: 1 }`
   - `("A","A-")` → `{ notches: 1, direction: "downgrade", wl: 0 }`
   - `("A-","A")` → `{ notches: -1, direction: "upgrade", wl: 0 }`
   - `("BB","BBB")` → `{ notches: -3, direction: "upgrade", wl: 0 }`
   - `("AAA","CCC-")` → `{ notches: 18, direction: "downgrade", wl: 2 }`
   - No test anywhere asserts 2 notches or WL 1 for BBB+ → BB+.
9. AC-9 [P1] (the calculator disagrees with notchChange on some pair; recounting is the workaround): Given all 361 ordered pairs `(p, c)` of `RATING_SCALE`, when `notchCalculator(p, c)` is called, then for every pair:
   - `notches === notchChange(p, c)`;
   - `direction` is `"downgrade"` when notches > 0, `"upgrade"` when < 0 and `"unchanged"` when 0;
   - `wl` is `0` when notches ≤ 1, `1` when notches === 2 and `2` when notches ≥ 3.
10. AC-10 [P2]: Given the same rating twice, when `notchCalculator("BBB","BBB")` is called, then it `deepStrictEqual`s `{ notches: 0, direction: "unchanged", wl: 0 }` and `Object.is(result.notches, 0) === true`.
11. AC-13 [P0], calculator part (a swallowed error returns WL 0 for an unscorable rating and hides a downgrade): Given an invalid rating, when `notchCalculator` is called, then the `RangeError` from `notchChange` propagates unchanged. The function returns no null, no 0, no object and no error object.
    - `notchCalculator("CC","BBB")` throws a `RangeError` whose message contains `"CC"`.
    - `notchCalculator("BBB","")` throws a `RangeError` (type only).
    - For the same inputs, the error's constructor is `RangeError` and its message is identical to the one `notchChange` throws.
12. AC-14 [P1], notch part (other POC parts import these names; a missing export breaks them loudly): Given `import * as n from "../../src/ratings/notch.mjs"`, when its keys are listed, then:
    - `Object.keys(n).sort()` deep-equals `["RATING_SCALE","notchCalculator","notchChange"]`;
    - `"default" in n === false`;
    - `typeof n.notchChange === "function"` and `typeof n.notchCalculator === "function"`.
13. AC-15 [P2], ratings part: Given `src/ratings/notch.mjs`, when it is reviewed and searched with grep (comments stripped), then:
    - nothing under `src/ratings/` imports from `src/indicators/` or contains the text `indicators/` in an import;
    - `notchCalculator` gets its distance by calling `notchChange(` and does not index `RATING_SCALE` itself;
    - the Ind. 13 WL rule is a separate named function, not exported, and carries a code comment saying the 1-notch difference from Ind. 12 (`countryRatingChangeWl`, WL 1) is intentional (B-36; the cross-check itself is AC-12 in T-02);
    - there is no import of `node:fs`, `node:net`, `node:http` or `node:process` (with or without the `node:` prefix), no `require(`, no dynamic `import(`, and no use of `console`, `Date`, `Math.random` or `process`;
    - there is no mutable module-level state (`let`/`var` at module scope);
    - `package.json` is unchanged and has no `dependencies` or `devDependencies` entries.

## Edge cases
- Trim applies to the outer edges only (String.prototype.trim). `"BBB +"` (inner space) does not match exactly and throws `RangeError`. `" bbb+ "` throws, and its message contains `" bbb+ "`. Both follow from the AC-5 rule; they are not extra pinned values.
- Just outside the scale: `"CC"` (one step below CCC-) throws. `"AAA+"` (above AAA) throws under the AC-5 rule.
- Wrong case anywhere throws: `"bbb+"`, `"Aaa"`.
- `Symbol("x")` must throw `RangeError` with `"Symbol(x)"` in the message. A template literal or `+` concatenation on the raw value would throw `TypeError` instead, which fails AC-5 and AC-6. The message must be built with `String(value)`.
- Both invalid: only `previous` is named. Valid previous with invalid current: the message names the current value as passed.
- Unchanged must be +0 in `notchChange` and in `notchCalculator().notches`. No negation and no `* -1` anywhere.
- `direction` values are exact lowercase strings: `"downgrade"`, `"upgrade"`, `"unchanged"`. `wl` is never 3 or 4 (capped at 2).
- The result object has exactly three own keys. No extra `previous`, `current` or `message` field.
- No try/catch in `notchCalculator`: the error object that reaches the caller is the one `notchChange` threw, not a wrapper.
- Frozen-array mutations throw only in strict mode. Test files are ESM and therefore strict.
- Tabs, newlines and other Unicode whitespace are accepted by `trim()` as a side effect. They are not pinned and not tested (plan risk).

## Test design
Unit tests are written by the dev in `test/ratings/notch.test.mjs` (import `../../src/ratings/notch.mjs`). Give it one top-level `describe` named after the module (e.g. `"ratings/notch"`) so QA can spot the file in the `npm test` output.

QA integration tests go in `test/ratings/qa/` (files `qa-*.test.mjs`, e.g. `qa-ratings-consumer.test.mjs` and `qa-ratings-purity.test.mjs`). Every QA test name starts with `qa-ratings:` so it is unique in the repo.
- QA imports the module the way a consumer does, through its public path (`../../../src/ratings/notch.mjs`, static and `await import(...)`).
- QA reads source files with `node:fs` (allowed in tests only). Before grepping, it strips `/* */` and `//` comments.
- A QA test must never spawn `npm test`, because that would run itself recursively.
