# T-01: Rating scale, notchChange and notchCalculator (src/ratings/notch.mjs)

**What to build:** a new pure ES module `src/ratings/notch.mjs` with three named exports and no imports:
- `RATING_SCALE`: the 19 grades, best first.
- `notchChange(previous, current)`: the signed notch count. Positive means downgrade, negative means upgrade, 0 means unchanged.
- `notchCalculator(previous, current)`: returns `{ notches, direction, wl }`, with `wl` following the Ind. 13 rule.

Each argument must be exactly one of the 19 codes. Any other value throws `RangeError`. Unit tests go in `test/ratings/notch.test.mjs`. `package.json` already has `"type": "module"` and `"test": "node --test"`, so it stays unchanged.

## User story
As a credit analyst, I want the notch change between two ratings counted the same way every time, with its direction and a suggested WL, so that I stop reading rating changes by hand and Ind. 12 (T-02) can build on one shared count.

## Acceptance criteria
1. AC-1 [P0] — a wrong scale shifts every notch count and every WL built on it: Given `import { RATING_SCALE } from "../../src/ratings/notch.mjs"`, when it is read, then `assert.deepStrictEqual(RATING_SCALE, ["AAA","AA+","AA","AA-","A+","A","A-","BBB+","BBB","BBB-","BB+","BB","BB-","B+","B","B-","CCC+","CCC","CCC-"])`, `new Set(RATING_SCALE).size === 19`, `RATING_SCALE[0] === "AAA"`, `RATING_SCALE[18] === "CCC-"`, and every minus is ASCII `-` (no element contains U+2212).
2. AC-2 [P0] — a wrong count gives Ind. 12 a wrong WL for every client: Given two valid codes, when `notchChange(previous, current)` is called on a downgrade, then it returns the integer `RATING_SCALE.indexOf(current) - RATING_SCALE.indexOf(previous)`: ("BBB","BBB-") → 1; ("BBB-","BB+") → 1; ("BBB","BB+") → 2; ("BBB+","BB+") → 3; ("AAA","CCC-") → 18.
3. AC-3 [P0] — a wrong sign turns an upgrade into a downgrade: Given two valid codes, when `notchChange` is called on an unchanged or upgraded pair, then ("A","A") → 0; ("CCC-","CCC-") → 0; ("BB+","BBB-") → -1; ("BB","BBB") → -3; ("CCC-","AAA") → -18. Unchanged is `+0`, not `-0` (`assert.strictEqual` tells them apart).
4. AC-4 [P0] — bad input that returns a number silently hides a downgrade: Given each `v` in INVALID, when `notchChange(v, "BBB")` or `notchChange("BBB", v)` is called, then it throws `RangeError` and returns nothing. `notchChange("BBB")` (current missing) also throws `RangeError`.
5. AC-5 [P1] — the helper suggests a wrong WL, but the analyst can still count by hand (REQ-06-02 is Should): Given a downgrade, when `notchCalculator(previous, current)` is called, then it deep-strict-equals:
   - ("BBB","BBB-") → `{ notches: 1, direction: "downgrade", wl: 0 }`
   - ("BBB","BB+") → `{ notches: 2, direction: "downgrade", wl: 1 }`
   - ("BBB+","BB+") → `{ notches: 3, direction: "downgrade", wl: 2 }` (the REQ-06-02 example as corrected by X-example-notches)
   - ("AAA","CCC-") → `{ notches: 18, direction: "downgrade", wl: 2 }`
6. AC-6 [P1] — an upgrade shown as a risk misleads the analyst, who has a workaround: Given an unchanged or upgraded pair, when `notchCalculator` is called, then it deep-strict-equals:
   - ("A","A") → `{ notches: 0, direction: "unchanged", wl: 0 }`
   - ("BB+","BBB-") → `{ notches: -1, direction: "upgrade", wl: 0 }`
   - ("BB","BBB") → `{ notches: -3, direction: "upgrade", wl: 0 }`
   - ("CCC-","AAA") → `{ notches: -18, direction: "upgrade", wl: 0 }`
7. AC-7 [P1] — a pair outside the examples gives a wrong helper result, with a workaround: Given every ordered pair (p, c) of the 361 pairs from `RATING_SCALE`, when `notchCalculator(p, c)` is called, then:
   - `Object.keys(result).sort()` deep-equals `["direction","notches","wl"]`
   - `result.notches === notchChange(p, c)`
   - `direction` is "downgrade" when notches > 0, "upgrade" when < 0, and "unchanged" when 0
   - `wl` is 0 when notches <= 1, 1 when notches === 2, and 2 when notches >= 3
8. AC-8 [P1] — the helper returns something for bad input, with a workaround: Given each `v` in INVALID, when `notchCalculator(v, "BBB")` or `notchCalculator("BBB", v)` is called, then it throws `RangeError`.

INVALID (plan.md) has 15 values:
- strings: `"bbb+"`, `" BBB+"`, `"BBB+ "`, `"BBB−"`, `""`, `"CC"`, `"C"`, `"D"`, `"NR"`, `"WD"`, `"Baa1"`
- non-strings: `null`, `undefined`, `42`, `{}`

## Edge cases
- **Ends of the scale (AC-2/3):**
  - ("AAA","AA+") → 1; ("AA+","AAA") → -1
  - ("CCC","CCC-") → 1; ("CCC-","CCC") → -1
  - ("AAA","AAA") → 0; ("CCC-","CCC-") → 0
  - ("AAA","CCC-") → 18 and ("CCC-","AAA") → -18 are the largest possible values.
- **Where letter groups meet (AC-2):** ("A-","BBB+") → 1; ("BBB-","BB+") → 1 (the investment-grade line); ("B-","CCC+") → 1.
- **The WL thresholds of the Ind. 13 rule (AC-5/6/7):**

  | notches | wl |
  | --- | --- |
  | -1 | 0 |
  | 0 | 0 |
  | 1 | 0 |
  | 2 | 1 |
  | 3 | 2 |
  | 18 | 2 |

  Example pairs: ("AA","A+") → `{2,"downgrade",1}`; ("BBB-","BB") → `{2,"downgrade",1}`; ("BBB","BB") → `{3,"downgrade",2}`; ("CCC+","CCC-") → `{2,"downgrade",1}`.
- **Signed zero:** unchanged gives `notches: 0`, never `-0`. A result of `-0` fails both `deepStrictEqual` and `strictEqual`.
- **Missing arguments (AC-4/8):**
  - `notchChange()` throws `RangeError`, and so does `notchChange("BBB")`.
  - `notchCalculator()` and `notchCalculator("BBB")` throw `RangeError`.
  - Both arguments invalid (`notchChange(null, null)`) throws `RangeError`.
- **Inputs beyond INVALID** (plan Scope: "every other input" throws; NFR-security: nothing is coerced). Each must throw `RangeError` in either position for both functions:
  - `new String("BBB")` (a String object, not a primitive)
  - `["BBB"]` (an array that coerces to "BBB")
  - `"toString"`, `"constructor"`, `"__proto__"`, `"length"` (traps for an object or index lookup)
  - `0`, `NaN`, `true`, `10n`
  - `Symbol("BBB")`, `Object.create(null)`

  Watch the error message for the last two and for `10n`. Putting them into a template literal or `String()` / `JSON.stringify` can throw `TypeError` instead of `RangeError`. The message may name the argument (`previous` / `current`) and `typeof v`, but it must never stringify the value. NFR-security review: no `String()` on the input.
- **Invalid input never gives a result:** no default value and no fallback to index -1. For example, `notchChange("BBB","NR")` must not return `-1 - 8 = -9`.
- **Results are independent objects:** two calls `notchCalculator("BBB","BB+")` return deep-equal results. Changing the first result (`r.wl = 9`) does not change the next call's result, because there is no module-level mutable state.
- **The error message text is not part of the contract.** Tests check only the type: `assert.throws(fn, RangeError)`.

## Test design
Levels:
- **unit:** the dev's `test/ratings/notch.test.mjs`, run by `node --test test/ratings/notch.test.mjs`.
- **integration:** QA's `test/ratings/notch.integration.test.mjs`, run by `node --test test/ratings/notch.integration.test.mjs`. It imports the module through its public path the way T-02 does. It is table-driven from the plan's example table, cross-checks the functions against each other, and must also pass under the full `node --test`.
