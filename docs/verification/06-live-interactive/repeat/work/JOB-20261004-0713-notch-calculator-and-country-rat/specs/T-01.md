# T-01: Rating scale, notchChange and notchCalculator in src/ratings/notch.mjs

## User story
As a credit analyst (through later POC screens) and as the Indicator 12 module, I want to give a previous and a current rating and get back the signed notch change, its direction and the resulting WL under the Indicator 13 thresholds, so that a rating move turns into a Watchlist level the same way every time (REQ-06-02, REQ-03-13, C2, C6).

What to build: create `src/ratings/notch.mjs`, a pure ES module with exactly three named exports: `RATING_SCALE`, `notchChange(previous, current)` and `notchCalculator(previous, current)`. A single private helper validates and normalises the inputs, looking them up in a private module-level `Map` built from the scale. Dev unit tests go in `test/unit/ratings/*.test.mjs`. QA integration tests go in `test/integration/ratings/*.test.mjs`. Every export gets JSDoc.

## Edge cases
- Trim follows `String.prototype.trim()`: `" BBB﻿"` and `"　A "` are valid and equal "BBB" and "A". A zero-width space is not trimmed, so `"​BBB"` throws RangeError.
- Look-alike non-strings throw RangeError and are never coerced: `new String("BBB+")`, `["BBB+"]`, `{ toString: () => "BBB+" }`.
- `7n` throws RangeError. `JSON.stringify(7n)` itself throws TypeError, so it must not format non-string values. An object whose `toString` throws must still give RangeError (building the message never throws).
- Prototype-key strings `"__proto__"`, `"constructor"`, `"toString"`, `"hasOwnProperty"` throw RangeError in either position.
- When both arguments are invalid, only previous is named.
- After the failed mutation attempts of AC-2, every result in the AC-3/4/6 tables is unchanged.
- The object returned by `notchCalculator` is a plain object with `Object.prototype`; mutating it must not change the next call's result. Tests must not assert whether it is frozen.
- AC-2 assignment checks need strict mode (`.mjs` is strict).
